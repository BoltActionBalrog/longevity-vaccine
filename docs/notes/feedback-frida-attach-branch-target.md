---
name: feedback-frida-attach-branch-target
description: Frida Interceptor.attach placement hazards — mid-function attaches are BANNED outright (any one permanently poisons [esp]-at-the-hook with an island pointer, onEnter-only included); safe hosts = clean function entries, ON-a-call-insn, or zero-Interceptor stubs/redirects
type: feedback
---

A Frida `Interceptor.attach` on x86 overwrites ~5 bytes at the hook address (and relocates the covered instructions into a trampoline). If ANY branch target — including a same-function **loop back-edge** — lands inside `(addr, addr+5)`, the jump lands mid-trampoline and executes garbage → hard AV. This is the in-function twin of the PRACX entry+3 lesson ([[project-smac-hud-scaling]]): v15's join at `0x456398` (3-byte `add ecx,5`) swallowed the 12-line loop head `0x45639b`; iteration 2 jumped into the patch and crashed at eip=0x45639b (bytes@eip = trampoline debris).

**Why:** attach sites are chosen for register liveness, but safety additionally depends on the CFG around the next 5 bytes — invisible in a linear disasm read.

**How to apply:** before arming any register-join hook, run a join audit (capstone over the containing function: (a) join is an instruction boundary, (b) no jmp/jcc/call target ∈ (join, join+5)). If a join fails, slide it to an earlier instruction where the values are still adjustable (v15 fix: 0x456398 → 0x456395, before both `+5` adds). Keep the audit list in sync with the hook's join table.

## Second hazard (v16 census, 2026-07-05): NEVER attach between a call's argument pushes

A join placed after a call's first arg `push` and before the `call` **corrupts an already-pushed stack slot** — it arrives at the callee as a Frida heap/code address. Verified: v15's join at `0x4b84ef` (between `push -8` and `call veh_draw`) turned the size sentinel `-8` into `0x2EE0C8F` → absurd zoom → box-6 unit icons silently DISAPPEARED (no crash!). Four-point evidence: both box-6 calls with a mid-push join corrupted exactly the slot pushed before the join; calls with joins **before the first push** (box-3 `0x4b4e28`) or **on the call instruction itself** (box-4 `0x4b6bf2`, lever S `0x62ADED`) read clean.

**How to apply:** place joins BEFORE the first push of the sequence, or do the rewrite in the callee's entry hook keyed on `this.returnAddress` and patching `[esp+argOff]` (v17 fix for the box-6 +11 x-adjust). The symptom is silent wrong-args, not a crash — census the callee's args (T3 pattern) when a draw mysteriously vanishes.

### #2 GENERALIZATION (2026-08-22, council runs 3-5 canary-proven; CONFIRMED by the clean v6 run — attaches removed → zero islands, zero crashes): EVERY mid-function attach permanently poisons [esp]-at-the-hook — onEnter-ONLY included, args or not

The mechanism behind #2 is not limited to arg-push windows: Frida's invocation tracking replaces the dword AT [esp] at the hook point with an island trampoline and relies on a `ret` flowing back through it to undo the swap. At a **function entry** [esp] is the return address → round-trips invisibly. At ANY **mid-function** point, [esp] is whatever the frame keeps on top — a saved register, a live local, a pushed arg — and no ret ever passes through the trampoline, so the island pointer stays there **permanently**. Council proto: attach at 0x426b25 (repaint body, onEnter-only register bias) put 0x2eX0b0f into repaint's saved-EDI slot (pop edi → garbage → show_hide button-loop AV); attach at 0x427661 (mid-exec seed writes) poisoned a live exec-frame dword (post-vote AV two calls downstream); attach at 0x426FC0 (diagnostic!) poisoned show_hide's frame. **Signature: same island page offset across runs, different base per launch** (0x2eb0b0f/0x2ed0b0f/0x2ec0b0f) — a real heap pointer never repeats its page offset like that. A canary armed at the hooked point reads CLEAN in its own callback (the swap happens after the callback returns) — the smash appears at the NEXT checkpoint.

**Companion lesson (council v5→v6, same forensics): a stack CANARY must be READ-ONLY.** v5's canary "restore-in-place" wrote its snap values through a base captured at a PREVIOUS invocation — after that frame died, later calls reused the stack and the "restore" poisoned their live saved-register slots (the v5 crash registers were literally the snap values). A watch that writes is itself a writer: canaries log-only, and null the watch base the moment the watched frame exits (its onLeave). Also don't read the watched slots AT onLeave — they're below ESP and Frida's own onLeave machinery has already reused them (pure noise).

**How to apply:** mid-function Interceptor.attach is banned outright — no "safe placement" exists (the old #2 advice "place before the first push" only relocates which slot dies). The safe hosts are: function entries (verified undetoured), attaches ON a call instruction (Frida relocates the call and the swap targets the ret slot that call itself pushes — the one mid-function shape that round-trips), and zero-Interceptor mechanisms: hand-assembled stub + E8 call_target_redirect (council v5's S/B levers), setInterval polls, render tracing.

Two attaches whose 5-byte windows touch (v18-20: `0x62ADED` call + `0x62ADF2` next insn) break execution even when each is individually sound: the first patch's trampoline back-jump lands ON the second patch's rewritten bytes. Proven by bisection: v15-17 patched only `0x62ADED` = title menu fine; v18-20 added `0x62ADF2` = menu strips (openitem.flc flics through that exact handler) reduced to stubs; v21 removed both = menu healed. Extra trap at that site: the flic chunk dispatch is a switch **jump table** (@0x62AEF0, entry [4]=`0x62ADF7`) — joincheck's linear branch-target audit CANNOT see jump-table targets. **How to apply:** never let two attach windows touch; near switch dispatches prefer a function-ENTRY hook on the callee keyed on `this.returnAddress` (the v21 fix: hook Buffer_copy_4 `0x5DFF00` entry gated on ret==`0x62ADF2`).

## Fifth hazard (2026-07-05, v24 + v26 crashes): the ENTIRE baked-detour/resume cluster is Frida-untouchable — detour bytes AND resume address

Attaching at a baked 6-byte detour site (thunk_btn_2dscale @`0x608365`: `68 {abs32} C3`) crashed as deferred state corruption (garbage vtable in the CALLER — MainWin_build's button loop, AV @`0x45AB2C`, [esp] = trampoline-page-looking address), not an immediate fault. **v26 then disproved the "attach at the resume instead" fix: attaching at the RESUME address `0x60836B` (ordinary `test eax,eax; je`, window audited clean) crashed IDENTICALLY.** A `push imm32; ret` cave-thunk re-entry into a Frida on-enter trampoline is itself unsafe. **How to apply:** never Interceptor.attach anywhere in a baked detour+resume cluster (detour bytes, the byte after, or the pushed resume address). To act "just after a baked thunk", hook a FUNCTION ENTRY the post-thunk code calls, or the containing function's entry/exit. **RE-CONFIRMED 2026-07-10 (tutwin v6.4/v6.5):** attaching at thunk_btn_shrink's own tail `push 0x607e85` (cave code, boundary verified, no branch targets in window) crashed identically (@0x45AB2C) even with a no-op callback. **Third escape hatch (tutwin v6.6): retarget the tail as DATA** — build a hand-assembled stub in `Memory.alloc` RWX (retain it on globalThis — alloc frees on GC!) ending `push <real resume>; ret`, then overwrite ONLY the 4-byte imm32 of the thunk's tail push to point at the stub. No Interceptor, no trampoline, the project's own call_target_redirect pattern at runtime.

**RECURRENCE (2026-07-19, hook_basewin7 v1):** attaching at thunk_btn_shrink's cave ENTRY (pcave2+0x400) with thunk_btn_bandstripe + thunk_bilinear_blit entries also hooked crashed at the SAME 0x45AB2C after three menu-button draws. The whole popup-button-zoom chain (shrink, 2dscale, tutbtn_post, btn_gate, bandstripe, bilinear, fillcap/devfill) is one detour-cluster family — no Interceptor anywhere in it, entries included.

**RECURRENCE (2026-08-21, hook_council_confirm v1):** attached at thunk_btn_2dscale's cave ENTRY 0xA0C480 (+ planned resume 0x60836B, the exact v26-disproven "fix") — boot AV at the SAME 0x45AB2C after the same three menu-button draws. The attach plan's hazard audit only swept patches.yaml sites/LE tokens. **How to apply: an attach set is not audited until it has been checked against every hazard in this note.** v2 escape: the cluster's inputs/outputs are static globals (face sprites 0x7FE624/50/7C, btn buffer 0x7FEC50, cave flags) — a setInterval POLL with change-dedup replaces every cluster hook with zero Interceptor.

**COROLLARY (2026-07-11): hazard-#5 fallout MASQUERADES as evidence about your payload.** The tutwin v6.4 crash was blamed on its PAYLOAD ("unGated rounding desyncs the HUD bracket-compose") and that became a recorded design constraint — but v6.4 and the gated v6.5 both attached in the cluster and crashed at the SAME site (0x45AB2C), v6.5 with ZERO callbacks fired. Re-running the identical unGated payload through the safe tail-redirect: no crash, all-res verified, constraint deleted. **How to apply:** a functional lesson recorded from a run that ALSO violated an attach hazard is unproven — before honoring such a constraint (gating a bake, adding a denylist), re-derive it with a clean mechanism, and when writing up a crash from a hazard-violating run, record only the hazard, not payload conclusions.

### #5 SOFT-FAILURE extension (CONFIRMED 2026-07-05 by the v27→v33 HUD band hunt)

The crash is not the only failure mode — there is a **silent** one: a draw call chain that starts at a **Frida-hooked call site** (relocated E8 in the site hook's trampoline) and ends with a **cave `push imm32; ret` tail into a Frida-HOOKED function entry** simply never executes the final callee. No crash, no log, no pixels — the HUD state-sprite draws (MENU/COMMLINK bands, planet art) vanished for six probe versions while plain-E8 arrivals at the SAME hooked entry (frame caps, tile internals) and a push;ret arrival whose chain started from a BAKED (unhooked) call site (fillcap→Buffer_tile_2) all worked. The lethal combination is **site-hook-at-the-call + entry-hook-at-the-chain's-push;ret-target** — either alone is fine. Proven by removal: v33 deleted both hooks and the sprites rendered immediately.

**How to apply:** before hooking a function ENTRY, census who enters it via cave `push imm32; ret` tails; if any such chain STARTS at another Frida attach (or you also need the call-site hook), pick a different host for whichever purpose you can move (v33 moved the bracket disarm from Sprite_draw_2 entry to GraphicWin_fill entry keyed on returnAddress — plain-E8-called, first op of the caller). When a draw goes missing WITHOUT a crash, suspect this before inventing engine mechanisms — audit your own attach set against the call chain first.

**RECURRENCE (2026-07-09, frame9 list-ring):** site attach at the baked call-redirect `0x48977F` (→thunk_factionwin_framecover) while the four renderers framecover tail-jumps into were `Interceptor.replace`d = the whole faction picker stopped drawing AND clicking crashed. `Interceptor.replace` at the push;ret target counts the same as an entry hook for this hazard. Fix: no hook at all — the picker window is a GLOBAL (buffer `0x822b5c`); locate the window base by value-scan and read fields (`+0x8704` pitch, `+0x86b0/b8` native list T/B, `+0x86bc` embedded Dialog) directly inside the replaced renderer.

## Sixth hazard (2026-07-10, UNEXPLAINED but 3/3-reproduced): mid-function attaches in Popup_calculate_dimensions / Popup_on_draw_background silently EMPTY the popups

`hook_namewidth.js` v1 attached at `0x404b7f` + `0x404bd0` (Popup_calculate_dimensions) and `0x406183` (Popup_on_draw_background) — every window audited clean over the WHOLE image (no branch/jcc/short-jmp AND no dword literal, i.e. no jump-table entry, lands inside any window; callbacks 100% read-only; PRACX patch/hook addresses nowhere near; identical harness). Result in 3/3 runs on BOTH exes: modal body text gone, Quit modal stripped to the lone default OK button, Dialog[+0x5C] collapsed to its 480 default — the popups genuinely built EMPTY, invalidating the measurement itself. Same exe/res/launch with the single Buffer_box_sprite-entry attach (hook_namefield.js) minutes earlier: content intact. Mechanism unidentified — treat these two functions (and by extension hot popup-build/draw internals) as **no-attach zones**; measure popup state from a callee-entry attach (Buffer_box_sprite entry: cave `0xA11740` on the patched exe / native `0x5E2DD3` on pristine — five 1-byte pushes, audited) reading fields off `popup = dest_buffer - 0x444` instead.

**How to apply:** when a mid-function attach passes every placement audit but modal/dialog CONTENT changes (items missing, defaults appearing), believe the content signal over the audit: bisect by rebuilding the probe on a proven attach host before trusting any number it logged.

## Seventh hazard (2026-07-11, prefwin v10, log-proven): site hook + hooked/detoured callee ENTRY on one chain = DISPLACED STACK at the entry + trampoline addresses leaking into engine state

When a Frida-hooked CALL SITE's callee entry is ALSO hooked (by Frida) or carries a baked E8 detour, the entry-side view of the stack is displaced by Frida trampoline dwords: prefwin v10's Dialog_init_2 ENTRY hook read ret=`0x2ee1c1f` and arg1=`0x2EE1C0F` (trampoline addresses) while args 2-4 read correctly — its "scale x" write therefore hit a trampoline slot (real x passed native) and could have corrupted the trampoline. Same for a find_font entry census against 7 hooked find_font sites. **The value-family signature: `0x02Exxxxx` dwords appearing in engine fields.** The PrefWin "mystery rect corruption" (`0x2EC0C8F` in rect+0x13c, hunted for 3 rounds as a phantom Win_move caller) and the button-label garbage (`"ÿ5"` = FF 35 code bytes rendered as text, labels pristine without Frida) are the same family — self-inflicted interplay, not engine movers. Also note hazard #2 recorded `0x2EE0C8F` for a corrupted push slot — same signature.

**How to apply:** (a) never hook a call site whose callee entry is Frida-hooked OR baked-detoured (BaseButton_init 0x607210, Win_move 0x5ED7D0, Buffer_box_sprite 0x5E2DD3, FlatButton-draw 0x607E50 are baked-detoured entries — their CALL SITES are off-limits too); scale instead at a clean deeper entry (e.g. GraphicWin_init 0x5D4EF0 gated on parent) or via static gates (fixed struct addresses). (b) When ANY `0x02Exxxxx`-shaped dword shows up in engine state or a hook's reads, audit your own attach set for site+entry pairs FIRST — before hypothesizing an engine writer. (c) Values read by an entry hook whose callers include hooked sites are garbage for those calls — census results must come from clean-caller entries only.

### #5/#7 RECURRENCE (2026-08-03, hook_prodpicker v1) + the guard-form trap

The ProdPicker trace attached at `BaseButton_init` 0x607210 and `Buffer_write_cent_l_7` 0x5DD130 — both baked `push imm32; ret` detours on the live exe — plus nine CALL SITES whose callee entries are detoured (GraphicWin_init 0x5D4EF0, Font_init 0x618F40, veh_draw 0x5594F0, BasePop_exec_3 0x602600). Symptom: the picker **drew all its cells and then closed instantly with the cancel sentinel, never appearing on screen** (soft failure, no crash), and a Font_init "size" arg read back as `0x02ED000F` — the #7 trampoline-dword signature. **The trap that let it through: the hook's own entry-byte guard tested only `E9`/`E8` and a baked detour is `68 <imm32> C3` — it starts with 0x68.** Guard on all three forms, or better: audit the whole attach set against the live exe up front (scratch `audit_attach.py` pattern — live-vs-`.bak` bytes at every attach VA *and* at every callee entry those sites call).

**How to apply:** prefer a v2 shaped as **function ENTRIES only, all verified undetoured, keyed on `this.returnAddress`** — then the site-hook + detoured-entry combination cannot arise at all. Most call-site reads are unnecessary: persistent struct fields can be read later from a clean host, and args pinned by a formula the first (hazard-tainted) run already confirmed exactly need no hook at all. Per the #5 corollary, numbers from the tainted run stay UNPROVEN until a clean run reproduces them — unless independently corroborated (here: a user screenshot whose measured button-row y matched the logged y exactly).

## Third hazard (same family): NEVER put onLeave on a call-instruction attach

Frida implements `onLeave` by swapping the "return address" at `[esp]` at the hook point. At a **function entry** `[esp]` IS the return address — safe. At a **call instruction** (or anywhere mid-function) `[esp]` is the last-pushed ARGUMENT — the swap corrupts it. Call-site attaches must be `onEnter`-only (those are proven safe: lever S capture, box-4 `0x4b6bf2`, E-lever). For post-call work, add a second `onEnter`-only attach on the NEXT instruction after the call (verify boundary + branch targets with joincheck) and pass state via a shared JS object (v18 levers Y/Z/S).
