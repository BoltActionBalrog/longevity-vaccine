In-game movies (intro, secret projects, end-game) drop the desktop to a tiny low-res blurry mode. Investigation 2026-06-22:

**Two layers.**
- VANILLA terranx plays movies *internally*: `amovie_project_2` @0x403BE0 (cdecl, const char* name) builds `movies\<name>.wve`, calls `set_video_mode` @0x4BEA50 (thiscall, ecx=ddwin, RET 0x10) at site 0x403CC0 to switch DirectDraw to **640x480x12bpp**, plays, restores via the 0x4BEA50 twin @0x403D8C. By-index wrapper `amovie_project` @0x403BA0 resolves index→name then calls _2 @0x403BD4. So native ALSO drops res (to 640x480) — not a free win.
- PRACX (what we run) **runtime-patches** the entry of 0x403BE0 with `0xE9` JMP→`PRACXShowMovie` (hook table entry `{_cx(0x407080,0x403BE0), PRACXShowMovie}` in PRACXHook() at DLL attach). PRACXShowMovie unconditionally `CreateProcess`es `MoviePlayerCommand` + ` .\movies\<file>`. Default `MoviePlayerCommand=<DEFAULT>` → `.\movies\playuv15.exe -software`. NO fallback value falls through to native.

**playuv15.exe** = EA UK "Play uV v1.50a" (1997), DirectDraw exclusive-fullscreen FMV player for .wve (uV/TQI codec). It does the SetDisplayMode→low-res = the desktop drop. CLI levers: `-window` (no fullscreen/no mode switch), `-xsize/-ysize` (stretch), `-software`, `-doublex/-doubley`. .wve assets tiny (opening 400x192, openingx 592x288, faction 320x240) → blurry upscaled to 4K. See [[feedback-smac-aspect-ratio]] before any stretch (clips have varying native AR).

**Settings to disable diversion:** none disables ONLY movies. `[PRACX] Disabled=1` unloads ALL of PRACX (DllMain returns FALSE) → fully vanilla low-res game w/ native 640x480 movie. Or run bundled vanilla `terranx.exe` (cc659f) / `terranx_pristine.exe`. Observation mode only.

**Native-render strategy (chosen route) — intercept ABOVE the hook.** PRACX's JMP only fires if 0x403BE0 is reached. Redirect every CALLER statically (call sites are uncontested — PRACX never touches them) → PRACX's stamp becomes dead code, full coexistence. Authoritative xref scan (work\scripts\scan_movie_xrefs.py over terranx_pristine.exe): **8 direct E8 calls to 0x403BE0** = 0x403BD4 (inside wrapper), 0x4F2B4B (base production), 0x524D06/0x524D28/0x5253F5/0x525407 (end-game), 0x52AB6D (control_game), 0x5B3681 (eliminate_player). Wrapper 0x403BA0 has 2 callers (0x4F2B20, 0x51602D) but both funnel through 0x403BD4, so the 8 cover everything. ZERO indirect/absolute-dword refs to either function. Redirecting the 8 rel32 disps = total coverage (mirrors the 8-site menu-strip group pattern). COLLISION CHECK DONE/CLEAR (2026-06-22): PRACX's full 28-entry hook table contains NONE of the 8 sites (only movie entry is 0x403BE1 = the entry-JMP rel32 we bypass); empirical prax.dll dword scan of each site..site+4 = all clear. So all 8 caller-redirects are uncontested by PRACX.

**BENCH TEST 2026-06-22 — BLOCKER FOUND: native movie code CRASHES under PRACX.** Built bench = full patch set + 8 redirects ACTIVE (temp patches with sites flipped confirmed, applied from .bak; MD5 a99f0776), launched real game. Result: trampoline works MECHANICALLY (it intercepted the opening movie — playuv15.exe did NOT spawn, so PRACX's external path was bypassed as intended) BUT the game crashed ~6s in with AV 0xc0000005, EIP in NON-CODE: VA 0x9B839E (.data BSS / zero-init globals) and VA 0x6718D8 (.rdata data) = a CALL THROUGH A NULL/UNINITIALIZED POINTER. Decisive control: setting DisableOpeningMovie=1 -> CLEAN BOOT (user-confirmed); live binary (redirect inactive) + opening movie -> fine. So the native amovie_project_2 body RAN (fault is deep in native code, not in our cave 0xA0Dxxx) then called through a movie/DirectDraw global the game never initialized — because PRACX always diverts amovie_project_2 BEFORE the body runs, so the native uV/DirectDraw movie subsystem is never set up while PRACX is loaded. (The maintainer's earlier "native works" observation was via PRACX Disabled=1 = NO PRACX, where the subsystem IS initialized.) IMPLICATION: "intercept above + run native" is not viable as-is under PRACX; step 3 is not just resolution — would need to initialize/substitute the native movie subsystem first. FORK: (A) Frida-trace trampoline->native body to find the exact faulting indirect call + null global (is init feasible?); (B) PIVOT to the simpler win that sidesteps init entirely — keep PRACX's external playuv15 but stop the res-drop via MoviePlayerCommand = `.\movies\playuv15.exe -software -window -xsize/-ysize` (solves the PRIORITY goal w/o native code). Bench artifacts (terranx_BENCH.exe + .bak, work\_patches_bench.yaml, work\_pristine_tmp.exe) are temp — clean up.

**FRIDA DIAGNOSIS 2026-06-22 (hook_movie_native.js, AV handler) — ROOT CAUSE CONFIRMED, native route BLOCKED under PRACX.** Trace of the bench (full set + active redirect): trampoline 0xA0D860 FIRED for the opening movie ("openingx", caller-ret 0x52ab72 = our control_game redirect site 0x52ab6d) -> native amovie_project_2 body RAN -> reached 0x4BEA50 with args (0x9B8398, 640,480,12). 0x9B8398 = the game's INSTALL-PATH STRING global ("D:\GOG Galaxy\..."), and the AV's EIP wild-jumped INTO that string (bytes@eip = ":\GOG Galaxy\Gam"). amovie_project_2 @0x403CC0 calls 0x4BEA50 (path/setup), then a chain 0x5FFDB0 / 0x5D4E40 / 0x4042C0 / 0x5D4DD0 — the 0x5D4xxx are Buffer/GraphicWin/DirectDraw-surface builders (0x5D4EF0=GraphicWin_init). So the native path constructs its OWN video surfaces = exactly what PRACX+DDrawCompat replace. Crash = native pipeline dereferencing video state that doesn't exist under PRACX (works fine with PRACX Disabled=1, per user's earlier pass). CONCLUSION: "intercept above + run native" is mechanically proven but a DEAD END under PRACX without reconstructing/initializing the whole native DirectDraw movie pipeline (large, fragile, fights PRACX for the display) — not worth it. RECOMMENDED PIVOT: keep PRACX's external playuv15 and kill only the resolution drop via MoviePlayerCommand = `.\movies\playuv15.exe -software -window -xsize <W> -ysize <H>` (zero binary patching, solves the PRIORITY goal). DECISION PENDING: back out the staged native_movie_player group (restore clean e920df04 MD5) since it can't work under PRACX, vs leave staged+BLOCKED. terranx.h note for 0x4BEA50 ("DirectDraw display-mode setter") is WRONG — it's a path/video-setup routine taking (this, char* path, w,h,bpp); fix if revisited.

**DirectDraw=0 avenue CLOSED 2026-06-22 (don't retry).** `[Alpha Centauri] DirectDraw` is a GAME setting (PRACX has NO DirectDraw option — confirmed in PRACX README/[PRACX] section). Read once at fn 0x45F9A0 with the "Video Mode" key: DirectDraw!=0 -> locked 1024x768/800x600 + hardware-DirectDraw surface flag (bit4); DirectDraw=0 -> desktop-res + GDI/software (no DD flag), known UI glitches in vanilla. Under PRACX it's a NO-OP: user flipped it to 0 on the live binary -> NO visible change. WHY: PRACX hooks the video init (its 28-entry hook table patches 0x5F018C, INSIDE Win_init_class 0x5F01F0 which writes ScreenWidth/Height) so it overrides the native 0x45F9A0 path entirely and always owns the DirectDraw device regardless of the flag. => Cannot make PRACX relinquish DirectDraw via settings; DirectDraw=0 does NOT give the native movie pipeline a non-conflicting path. Native route conclusively blocked by PRACX architecture (only escape = modify prax.dll to render movies / share its surface = big, and native STILL drops to 640x480). PIVOT to windowed playuv15 stands.

CORRECTION 1 (REVISED 2026-06-28 via full decompile — supersedes an earlier analysis's "no in-exe decoder"). There ARE TWO movie subsystems and amovie_project_2 picks by file: (A) movies\<name>.wve (= every GOG cinematic) -> the FIRST filefind succeeds -> set_video_mode 0x4BEA50 = an IN-EXE EA "Play uV"/TGV PLAYER (statically linked, FUN_005C9xxx-FUN_005Cxxxx cluster). Chain: movie_play_open 0x5CAE80 -> uv_container_open 0x5CB050 (mmioOpenA + EA magics SEAD/SCHl/1SNh, allocs 1.2MB frame + 300KB audio bufs) + uv_dsound_init 0x5CE340 (DirectSound) + uv_ddraw_surfaces 0x5CBE30 (DDraw surfaces) + spawns uv_decode_thread 0x5CB220 (24-frame ring, loops uv_decode_frame 0x5C9EC0 = the EA chunk demux/decode core: reads 8-byte chunk hdr via mmioRead, dispatches SCHl/SCCl/SDCl/SECl/TGV*). (B) fallback exts (registry/k_game paths) -> Movie_player 0x404070 -> MCI avivideo (Movie_mci_open 0x5FFF90 etc) -- a SEPARATE legacy path, NOT used for .wve. So an earlier analysis traced only path (B) and wrongly concluded "MCI-only / no decoder". The "Play uV ... Martin Griffiths EA UK 1997" string @0x691F08 is a dead STRING (no xref) but the uV CODE is linked + active. => "reuse the native decoder" IS in principle possible (the uV cluster works), but it's tightly DDraw+DirectSound-coupled (decoded frames go to a DDraw surface via uv_present_frame 0x5CC940), so libav remains the cleaner presenter route; reuse would mean intercepting the decoded frame buffer before uv_present_frame.

CORRECTION 1b (REVISED 2026-06-28 — my own earlier "pristine drops res at 4K" claim was WRONG on its premise; here is the verified reconciliation). The Pristine.lnk shortcut runs terranx.exe (vanilla cc659f) with NO args; it reads [Alpha Centauri] DirectDraw, and Alpha Centauri.ini has **DirectDraw=1** -> pristine runs **1024x768 fullscreen-EXCLUSIVE, NOT 4K** ([PRACX] ScreenWidth=3840 applies only to terranx_PRACX.exe). User was right about 1024x768. The .wve cinematics DO call movie_ddraw_fs_init 0x4BF4B0 = DirectDrawCreate -> SetCooperativeLevel(phWnd, EXCLUSIVE|FULLSCREEN) -> IDirectDraw2::SetDisplayMode(640,480) -- so there IS a 1024->640 DDraw mode-set -- BUT because pristine is ALREADY exclusive-fullscreen, that switch happens under the game's display ownership and NEVER exposes/reflows the desktop. That is exactly why the maintainer observes "no resolution change" / no disruption. The DISRUPTIVE kind (desktop icon reflow) only occurs when the game runs at DESKTOP res in non-exclusive/borderless mode -> that is PRACX (borderless at 4K), NOT pristine-as-shipped. => The movie res-drop problem is PRACX-SPECIFIC. Pristine (DirectDraw=1, 1024x768 exclusive) needs NO movie fix; its cinematic flow is already fine (user-confirmed). The presenter would only be needed for a FUTURE pristine target deliberately run at desktop res (DirectDraw=0 / 4K). So the original "motivation weaker for pristine" instinct STANDS; my intervening "equally disruptive at 4K" claim was based on the false premise that pristine runs at 4K. (Aside: movie_ddraw_fs_init creates its OWN DDraw device regardless of the game's DirectDraw setting, so IF pristine were ever run at desktop-res non-exclusive, the .wve path WOULD yank the desktop -> then the presenter applies; pristine-at-desktop-res also renders the game via GDI so the same StretchDIBits->phWnd target would work, only the intercept hook + DLL loader differ.)

CORRECTION 1c (VERIFIED 2026-06-28 via the DDrawCompat runtime log of an actual pristine run) — PRISTINE MOVIES ARE ALREADY UPSCALED TO 4K WITH NO RES CHANGE; the game's ddraw.dll IS DDrawCompat and pristine loads it. CORRECTION 2 — PRACX presents via GDI, NOT a DirectDraw flip. PRACX kills HW DDraw (`xor esi,esi`@0x45F9D0, pracx.cpp:2464), runs a borderless WS_POPUP window at DESKTOP res, and presents each frame by GDI BitBlt/StretchBlt (PRACXWindowBitBlt hooked @0x5F018B) from the game's DIB-backed CCanvas to the window DC.
